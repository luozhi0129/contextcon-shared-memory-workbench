What the measurement actually says

At this scale — 5 memories, 3 traces, one relay — recall costs about the same as re-pasting, and slightly more (170 tokens, 20.5% on this run). The reason is visible in the run log: retrieval is imprecise at small scale. The reviewer's recall returned the coder result twice (identical text, two memory ids) plus a verdict it did not need; the researcher and coder each recalled 3 memories when 1 would do. The re-paste baseline, by contrast, is exactly the texts needed and nothing else.

That is the honest result for a toy relay — and it is the point. The saving is not in a single handoff at toy scale; it is in how the two costs grow:

  • Re-paste grows with history: every new memory and every new trace turn

has to be pasted again at the next handoff. - Recall stays bounded by the retrieval limit (5 memories here): the agent asks a question and gets the top matches back, however long the history is.

Projection (model from measured per-unit costs, NOT a measurement)

Measured per-unit costs: one memory ≈ 98 tokens (mean of the 3 distinct task memories), one trace turn ≈ 62 tokens (mean of the 3 traces). Each further relay iteration adds ≈ 381 tokens to the paste baseline (2 new memories + 3 new traces). The recall cost stays near its measured per-relay level (1000 tokens) because each agent's recall is capped at the configured limit of 5 memories; the formal ceiling is 2037 tokens (3 agents × (longest query + 5 × longest memory)). Assumptions, stated plainly: history grows by whole relay iterations (2 new memories + 3 new traces each); each new memory/trace costs the measured mean; retrieval never returns more than the configured limit of 5 memories. If the task's memories get longer, the paste baseline grows faster; the recall level does not move. The crossover — where the re-paste baseline first passes the measured recall level — is at roughly 7 memories on this model (one more relay iteration); it passes even the formal recall ceiling (2037 tokens) at roughly 13 memories.

Two findings from this phase (not part of the token count)

1. Relay trace turns were never persisted. agents/common.py::trace() passed datapack_id to conversation_add_message, which the server rejects with not_found (the conversation is created without a datapack_id, so it lives in the default datapack). The drivers never checked the return value, so 6 trace calls across the two relay runs silently failed. The trace texts in this comparison are therefore reconstructions from source + run log (exact strings), not stored copies. Fixed in this change: trace() no longer passes datapack_id. Verified by direct probe: the same call without datapack_id returns status: accepted and the turn appears in conversation_get ~1 minute later (async indexing — an immediate re-get still shows 0 messages). USAGE.md's earlier line "conversation_add_message accepted: 6" was inferred, not verified, and is corrected there. 2. context_search responses carry a token_savings field (total_tokens: 10000 on the probe call). Its definition is unverified — it did not move in an obvious way and 10000 is suspiciously round — so it is not used as evidence anywhere in this comparison.
